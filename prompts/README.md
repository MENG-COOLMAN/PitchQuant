# Prompt 规范集 · Prompt Specifications

> **这是 PitchQuant 最独特的部分**：不是统计公式，而是**如何用规范管住一个大语言模型**——让它按流程走、不偷懒、可审计、能被证伪。

---

## 🔁 四件套闭环

```
         ┌─────────────────────────────────────────────────────┐
         │  ① 分析执行规范   prompts/01-analysis-pipeline.md    │
         │     LLM 按 9 步流程执行：数据 → 方向 → 专项 → 比分    │
         └───────────────────────┬─────────────────────────────┘
                                 │ 产出：一场完整分析
                                 ▼
         ┌─────────────────────────────────────────────────────┐
         │  ② 完成度检验   prompts/02-completeness-check.md     │
         │     逐项核对：步骤/参数/数据/传导/模块活跃性          │
         │     发现遗漏 → 立即补充 → 更新结论（不重复已完成）     │
         └───────────────────────┬─────────────────────────────┘
                                 │ 产出：完成度报告 + 修正后的结论
                                 ▼
         ┌─────────────────────────────────────────────────────┐
         │  ③ 结果审计   prompts/03-result-audit.md             │
         │     独立审计：Step0-10 逐项 + 传导链 + 数值证据       │
         │     原则：未列出 = 未执行（宁严勿松）                 │
         └───────────────────────┬─────────────────────────────┘
                                 │ 产出：审计报告（通过/不通过）
                                 ▼
                     （模型迭代时，用于模型本体）
         ┌─────────────────────────────────────────────────────┐
         │  ④ 模型工程审计   prompts/04-model-audit.md          │
         │     12 项探查 → 8 维审计 → 修复 → 全量回归           │
         │     核心：存在 ≠ 活跃（必须实际运行验证）             │
         └─────────────────────────────────────────────────────┘
```

**设计哲学**：`①规范行为 → ②自检纠偏 → ③外部审计 → ④工程体检`
四者**互相闭环**：①要求"输出必须被消费"，②就检查"是否被消费"，③审计"是否有证据"，④验证"运行时是否真的生效"。

## 📄 文档清单

| 文件 | 用途 | 触发时机 | 核心机制 |
|:--|:--|:--|:--|
| **`01-analysis-pipeline.md`** | 单场分析执行规范 | 收到赔率数据时 | 9 步流程 + 7 条铁律（无遗漏/无弱化/无参数缺失…） |
| **`02-completeness-check.md`** | 分析完成度检验与补充 | 分析完成后、输出结论前 | 4 维检验 + 遗漏分级 + 补充后必更新结论 |
| **`03-result-audit.md`** | 单场分析结果审计 | 需要独立复核时 | Step0-10 逐项 + 11 条传导链 + 数值证据 |
| **`04-model-audit.md`** | 模型本体全面审计 | 模型迭代更新后 | 12 探查 + 8 维（含实际运行验证）+ 7 步闭环 |

## 🚀 怎么用

### 场景 A：你要分析一场比赛
```
1. 把 01-analysis-pipeline.md 作为系统提示词（或粘贴在对话开头）
2. 提供赔率数据（格式见 01 的「输入说明」）
3. LLM 按 9 步执行 → 输出完整结论
4. （推荐）再用 02-completeness-check.md 让它自查一遍
```

### 场景 B：你要复核一份分析
```
把 03-result-audit.md + 分析报告 一起给 LLM
→ 得到逐项审计结论（哪些项没做/数值缺失/传导断裂）
```

### 场景 C：你改过模型，要体检
```
把 04-model-audit.md 作为指令
→ LLM 先动态探查你的实际文件结构（不假设数量/版本）
→ 8 维审计 + 实际运行验证 → 修复 → 全量回归
```

## ⚙️ 适配说明（重要）

这些规范由**具体实现**中提炼，但**故意不绑定实现**：

| 规范里写的 | 含义 | 你该如何适配 |
|:--|:--|:--|
| "预计算脚本" | 一次性算出全部确定性指标的脚本 | 对应本仓库 `scripts/tmp/calc_all.py`，或你自己的等价物 |
| "现场比分引擎" | 多源融合生成比分概率的模块 | 对应 `live_score_engine.py` / `calc_poisson.py` |
| "联赛子模型" | 按联赛分别校准的规则集 | 对应 `skills/SK-league-*/` |
| "一致性校验" | 规则/文档/数据同步检查 | 对应 `scripts/tmp/check_sync.py`（公开版需完整模型文件，见 README 已知问题） |
| "全量校验项" | 不写死数量 | 你的项目有多少校验项就是多少 |

**🔴 原则**：规范写的是**行为要求**（"必须传全部参数"），不是**具体实现**（"调用 xxx 函数"）。任何等价的实现都能满足。
